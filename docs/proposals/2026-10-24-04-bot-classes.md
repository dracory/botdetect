# Proposal: bot classification

Status: proposed
Date: 2026-10-24
Spikes: `docs/spikes/go-ua-parser/README.md`,
`docs/spikes/aibouncer/README.md`

## Problem

`IsBot` returns a flat bool, but consumers need to *differentiate*: block
scrapers and scanners, allow search engines (SEO), maybe allow or observe
AI crawlers, never block user-initiated fetchers like `ChatGPT-User`
(a human clicking a link in ChatGPT).

## Proposal

Introduce a class taxonomy (adopted from go-ua-parser's `Bot.Class`,
mirroring aibouncer's `Purpose`):

```go
type BotClass string

const (
    ClassSearch  BotClass = "search"   // Googlebot, Bingbot, ...
    ClassSocial  BotClass = "social"   // Twitterbot, Slackbot, ...
    ClassAI      BotClass = "ai"       // GPTBot, ClaudeBot, ...
    ClassSEOTool BotClass = "seo-tool" // AhrefsBot, SemrushBot, ...
    ClassMonitor BotClass = "monitor"  // UptimeRobot, Pingdom, ...
    ClassScraper BotClass = "scraper"  // curl, scrapy, headless, ...
    ClassOther   BotClass = "other"
)
```

- Classification map keyed on bot identity (uasurfer named constants +
  our pattern hits) — a lookup, not a new detection mechanism.
- Detection APIs return a richer result, e.g.
  `Detect(ua) (Detection{Bot bool, Name string, Class BotClass})`, with
  `IsBot` remaining as the simple bool wrapper.
- User-initiated fetchers (`ChatGPT-User`, `Perplexity-User`) classify
  `ClassAI` but map to a "user" purpose — class alone shouldn't mean
  block; document this.

## Impact

- Middleware policy can allow `search`, block `scraper`, observe `ai` —
  the use case that motivated botdetect's existence.
- Stats can break down bot traffic by class in statsadmin.

## Open questions

- Exact class set — go-ua-parser's 7 vs aibouncer's 5 purposes; pick one
  canonical set.
- Unclassified pattern hits map to `ClassOther` — acceptable, or
  should unknown-pattern hits flag "unclassified" for triage?
